# Integration progress — development branch

This is an interim phase report, not a final acceptance or deployment report. No production accounts or databases were accessed, no deployment was made, and no cohort/model artifacts were regenerated. Work is on `arena/74d3a29f-pranaguard-copd-digital-twin`.

## Phase 1 — audit

- **Changed:** documented routes, endpoints, data sources, scientific boundaries, baseline issues and test strategy in [INTEGRATION_INVENTORY.md](INTEGRATION_INVENTORY.md), before implementation edits.
- **Preserved and inspected:** 120 original profiles, 172,800 hourly observations, original IDs, existing model bundle, 24/48/72-hour features and thresholds, historical environmental cache and provenance.
- **Incomplete:** the deployed Vercel/Render configuration, live database and provider credentials could not be independently inspected; repository deployment configuration alone is not proof of live state.

## Phase 2 — preservation and access foundation

- **Changed:** research APIs now require a doctor session and an explicit assignment to every existing synthetic record in portal mode. The unscoped WebSocket is limited to isolated legacy mode; the research interface uses its existing polling fallback. Added a local administrative `assign-cohort` operation for the existing verified synthetic cohort. Startup bootstrap no longer overwrites existing account passwords and can explicitly assign that original cohort. Explicit synthetic provisioning now creates a random one-time password rather than a predictable one, and still requires the patient to change it. Research UI requires a doctor session and includes logout. Research and care now share the clinician sidebar and selected patient in the integrated dashboard, while the previous `/doctor/care` route remains available. Matching expired/revoked portal sessions redirect to sign-in with an explanation without confusing legacy write-token errors for session expiry.
- **Preserved:** original research endpoint contracts and components, model, replay engine, cohort and portal assignment checks. Unsafe legacy mode remains separate; never use it with real patient data.
- **Passed:** new backend tests for anonymous/patient/partial-assignment denial, full-cohort doctor access, password preservation on repeated bootstrap and the cohort assignment command. Real Chromium against a disposable database loaded the 120-patient overview, advanced replay one hour, opened explainability, ran a what-if scenario, loaded validation, followed research → care → research with selected ID preserved, and logged in five synthetic patient accounts while denying cross-patient and research access.
- **Incomplete:** this is deliberately a conservative **whole-workspace gate**, not individually scoped legacy endpoints. Any additional unassigned record blocks the research workspace; an added non-synthetic record blocks it entirely. Portal-mode registration now atomically assigns the new fictional record to its registering doctor, but other doctors are not automatically assigned it and can therefore be blocked. Legacy registry, devices and global notification operations still need precise record-level authorization before the two workspaces can be treated as a production-ready unified application. The legacy WebSocket is unavailable in secure mode, and a configured legacy write token is still required for writes when set. The local browser exercised doctor-session revocation; more expiry, patient-session and concurrent-tab cases should still be tested. Five accounts were created for local tests only; no live demo credentials exist from this work.

## Phases 3–4 — initial design and entry points

- **Changed:** redesigned the homepage around body × environment, replay, horizons, explanation, clinician review and limitations, using a conceptual diagram rather than invented metrics. Added sign-in loading state and password visibility toggle. The research sidebar now uses a single scrollable rail rather than clipping navigation in two separate scroll areas.
- **Passed:** real Chromium captured the landing page at 1440×900, 768×1024 and 390×844 with no document-level horizontal overflow; desktop and mobile captures were visually inspected: [desktop](screenshots/integration/home-desktop.png), [mobile](screenshots/integration/home-mobile.png). Build and frontend tests passed.
- **Incomplete:** this is not the full reusable design system, comprehensive patient redesign, complete research dashboard redesign, or accessibility audit requested.

## Phase 5–6 — research and care integration

- **Changed:** the historical cohort view now shows 24/48/72-hour values, actual state timestamps, selectable horizon/ID/city/time sorting and the original 72-hour category filters. It labels unsupported states unavailable in the table and explicitly explains that unchanged backend cohort counts and means include such states. Care workflows render within the research dashboard's existing sidebar instead of forcing a navigation to a separate shell. A patient selected in either area is carried into the other. Existing care URLs remain usable. The care selector now searches and paginates assigned records instead of displaying all 120 at once. Portal-mode fictional registration atomically creates the record, assigns it to the registering doctor, and writes an audit entry; failure rolls back all three. The original 120-patient prediction cohort is unchanged. Newly registered records have an explicitly non-predictive care profile and city context, without a fabricated historical twin. A doctor-only, assignment-scoped review queue lists pending symptom check-ins, sputum entries, uploads and daily-care entries, plus due follow-ups, directly from SQLite. Queue order is by timestamp, not clinical severity; it displays at most 200 entries and explicitly notes the limit. Selecting a queue entry opens that patient rather than jumping directly to the specific record.
- **Passed:** new backend test confirms a patient cannot call the queue and a doctor cannot see entries for an unassigned patient. Real Chromium verified sorting against actual backend 24-hour values, no document overflow on the mobile cohort view, a single visible sidebar, opening a queued test check-in, searching and selecting another patient, preserving that ID on return to the research twin, opening a care deep link, a 390px care view without document overflow, and sign-in redirection after the browser session was revoked. A second Chromium journey registered a fictional record, checked the 120-patient cohort remained unchanged, opened its assigned care profile and city context, then confirmed the unsupported historical prediction boundary and preserved patient context. The repeatable scripts are `frontend/e2e/unified-navigation.mjs` and `frontend/e2e/registration.mjs`; run it only against an explicitly provisioned disposable database, with its required environment variables.
- **Incomplete:** individually scoped research/registry/device endpoints, full integration of all notification types, review queue filtering/pagination beyond the 200-item cap, and exhaustive patient-context/deep-link cases remain. `/doctor/care` remains an alternate standalone shell for compatibility.

## Phases 7–9 — current verification and remaining work

- Existing connected-care Chromium E2E passed against a separate fresh synthetic DB: provisioning, forced change, patient check-in, sputum photo, meal/water/activity entries, plan versions, clinician review, notification navigation and negative record/role checks. It did not validate every action or viewport. Five-patient local login checks did not exercise every workflow for every account.
- Frontend: **47 tests passed**, production build passed, npm audit reported **0 vulnerabilities** at the moderate threshold.
- Backend: **100 passed, 1 failed** using Python 3.11 and compatible independently resolved packages, not the pinned environment. The failure is `test_protected_scientific_and_design_files_are_byte_identical`: the old `docs/enhanced/BASELINE_MANIFEST.json` expects a different `frontend/src/styles.css` hash. `git show HEAD:frontend/src/styles.css` confirms the mismatch already existed at this branch's base commit. All other files listed in that manifest match. The historical manifest was not rewritten to conceal the mismatch. One upstream Starlette TestClient deprecation warning was emitted.
- Exact pinned runtime/dependencies were not tested: this sandbox has Python 3.11; `pyproject.toml` states Python ≥3.13. Test in the project's supported pinned environment before release.
- Remaining: implement properly scoped research/registry/device endpoints; complete cohort registry and review-queue enhancements, environmental visualizations supported by real source data, patient design, wider expiry/revocation coverage, responsive and accessibility coverage; exercise every required doctor/patient workflow and error case. Full production end-to-end testing has not been performed.
