## Initial prioritized issue register

- **Critical:** Partial doctor receives 403 for overview rather than an assigned-only cohort; insecure shortcuts would leak other patients. Preserve full-cohort validation gate and original research outputs. Add two-doctor, zero-assignment, non-synthetic and aggregate tests.
- **Critical:** Remaining whole-workspace operations are restricted to one fully assigned doctor; complete per-record concurrency and independent security review are outstanding. Never open a global operation to make the UI appear functional.
- **Critical:** Production persistence, uploads, backups, deployments, account linkage and live isolation are unverified. Do not run resets or modify production data.
- **High:** Research default selection uses replay demo patient even when not assigned; stale/query-string IDs and empty cohorts need safe handling.
- **High:** Research overview failure is rendered as backend unavailability even for HTTP permission failures. Distinguish HTTP, network and invalid-response errors.
- **High:** Research registry and care provisioning are separate experiences. Full canonical patient-management redesign and complete workflow semantics require further implementation and regression testing.
- **Medium:** Notification test/email, simulated devices, replay and provenance remain restricted in multi-doctor databases. Screen and action status should explain restrictions.
- **Medium:** Responsive/automated accessibility checks have historical local evidence, not a complete manual screen-reader, keyboard, zoom or live browser review.
- **Low:** Additional design-system and navigation consolidation requires preserving existing functionality and scientific/safety labels.

## Phase 3 — login abuse protection (2026-11-07)

- Added migration 008 for persistent, case-insensitive hashed-username failure windows. Five failed login attempts in a 15-minute fixed window block further attempts for that username until expiry, including when the username does not exist. A valid login clears its window; trusted local password reset clears the target window and revokes sessions. The database write lock rechecks the throttle and current password hash before issuing a session. Temporary credentials remain single-use. No plaintext passwords are logged or stored.
- This is deliberately limited: an attacker can lock a known username, password spraying across many usernames is not prevented, and registration/password-change endpoints are not rate-limited. IP/distributed edge protection, request limits, monitoring and a safe recovery process are still required.
- Local tests cover valid and nonexistent usernames, case folding, successful reset, expiry/restart, concurrent failures, administrator reset, and preservation of prior records when upgrading from migration 007. Hosted production migration and infrastructure remain unverified.
- Final local suites after the throttle change: pinned Python 3.13.10 backend **130 passed** (one Starlette/httpx deprecation warning); Node 22.22.3 frontend **71 passed**, build passed, npm audit 0. A disposable Chromium login journey confirmed five generic failures, denial of a correct password while blocked, the retry header and an accessible error. Earlier 96-scan and patient-management browser checks predate this login-only change.

## Phase 4 — paginated care queue (2026-11-07)

- Added bounded server pagination, type filtering and timestamp order for the doctor review queue. The page and count share a SQLite read snapshot and are scoped to currently assigned synthetic records. Check-ins and uploads in Pending Review, Under Review and Follow-up Required remain visible; sputum/daily entries are listed when Pending Review, and dated follow-ups when due and not completed. A related submission and follow-up may both appear. Counts and order describe documentation, not clinical urgency. Offset pages can shift when records change between requests.
- The UI exposes queue filters, ordering, page controls, counts, loading/error/empty states, and selection. Selecting a queue row opens the patient rather than the specific submission. Patient detail histories are capped at 100 check-ins/uploads/reviews and 500 sputum/daily entries, so older queued records may not be accessible from those screens. Direct record navigation, other workflow semantics and comprehensive manual accessibility remain open.
