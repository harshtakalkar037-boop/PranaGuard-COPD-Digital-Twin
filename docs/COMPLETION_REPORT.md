# PranaGuard connected-care engineering report

## What is implemented

- **Patient:** symptom check-ins now include additional symptoms and review status. A dedicated sputum diary supports chronological observations, privately stored optional PNG/JPEG photos, patient edits with prior snapshots, review status and shared clinician reviews. A daily-care page shows clinician-entered plan details and records meal status/notes, millilitres of water, and activity, duration, effort and comments. The dashboard shows recorded daily progress without a health score. It includes the requested food, fluid-restriction and exercise safety notices and never invents a hydration target or activity prescription.
- **Doctor:** assigned-patient summary counts, review states and follow-up counts; scoped symptom and sputum timelines; privately viewed photos; daily activity with type/date/review filters; doctor reviews and optional shared notes; and versioned care-plan creation, modification and deactivation. The Care Action Centre includes existing synthetic risks and timestamps, symptom and sputum data, daily activity, history, shared follow-up and environmental context. Patient-reported omissions are not labelled non-compliance.
- **Connected:** role- and record-scoped APIs share the existing SQLite Store and FastAPI application. New check-ins, diary entries, photos and daily records notify assigned doctors; shared reviews and care-plan changes notify the linked patient. Notifications persist with read state and navigate to the relevant portal view. No SMS or email is claimed.
- **Onboarding:** administrators create doctors and explicitly assign existing synthetic profiles locally. When the synthetic-only demo switch is enabled, assigned doctors may provision an unlinked synthetic profile, with a one-time displayed, hashed temporary credential and mandatory first-login password change. Local administrators can issue a random one-time reset and revoke prior sessions. No real identity is mapped to an arbitrary synthetic profile.
- **Existing research:** model files, evaluation results, synthetic cohort and feature calculations are unchanged. Scoped explainability, what-if and validation are available in the doctor portal. Environmental context retains source, observation/retrieval times and historical/fallback indicators. The patient summary is simplified. City-level conditions are not personal exposure.

## Database and security

Migrations `004_daily_care.sql` and `005_admin_audit.sql` add patient-reported diary entries and edit snapshots, diary reviews, versioned care plans, daily records and reviews, password-change state, and doctor/admin audit records. They extend the existing checksum-verified transactional migrations; no tables or cohort are reset. Foreign keys and indexes are used. Back up the SQLite database with its backup API and the private file directory before first startup after upgrade. Migration is automatic; see [setup and demo instructions](PORTALS.md).

Passwords use salted scrypt; only token hashes are persisted, tokens expire after eight hours, logout and password changes revoke sessions. Protected APIs validate role and patient ownership or doctor assignment. Private uploads use server-generated names, file signature/size checks, non-public storage and authenticated downloads. Patient-submitted records derive patient identity from the session. Daily care has an idempotency key; forms disable repeat submission while saving. Doctor review and plan actions and local administrative actions are recorded. The predictable initial password is **disabled by default** and is only permitted for explicitly assigned synthetic records with the demo switch enabled. The first-login gate is enforced on the backend.

**Not production ready:** browser session storage remains JavaScript-readable; no MFA, identity verification, rate limiting, secure recovery channel, encryption at rest, malware scanner, comprehensive access audit, retention policy, regulatory controls or independent security/clinical validation. Reverse-proxy upload body limits, TLS, security headers and a hardened deployment are required. Signature checking is not malware detection. Public patient registration remains vulnerable to abuse. The CLI reset requires a trusted operator and secure credential delivery. Never enter real patient information. External clinical decisions and automatic treatment are deliberately absent.

## Legacy isolation and known gaps

Legacy demo endpoints expose the cohort without per-patient access controls. They remain disabled by default and must only be enabled in a separate isolated synthetic database; enabling them disables the new portal APIs. Device simulation, replay and the original advanced charts/data-source screens are therefore available only in that isolated mode, not in the protected portal. The doctor cannot create a brand-new clinical record; the local admin must first assign an existing synthetic profile. Linking/unlinking and broader assignment management have no administrator UI. Follow-up due counts reflect review records, not a dedicated scheduling system. Diary history is limited to the latest 500 entries, daily history to 500 per query, symptom history to 100 and notifications to 200; date/review filters are not a substitute for full pagination. No browser-based test covers every notification trigger, responsive breakpoint, page, or failure path. No accessibility audit, penetration test or real clinical validation has been performed.

## Setup, demo, testing and reset

[PORTALS.md](PORTALS.md) contains startup commands, migration/backup instructions, administrator doctor provisioning, synthetic patient assignment, one-time patient credential workflow, the doctor/patient demonstration sequence, an isolated demo-only reset, and browser test setup. The predictable demo password must never be used on a public network.

## Executed verification

- Backend: `pytest backend/tests -q`: **95 passed**. Includes additive migrations, existing scientific/legacy functionality, isolated portal authorization, password change, check-ins, diary editing/photos/reviews, plan versions, daily logs, notifications and cross-patient restrictions.
- Frontend: `npm ci`, `npm test`: **38 passed**; `npm run build` passed. Vitest was upgraded to 4.1.12 to address development dependency vulnerabilities; `npm audit --audit-level=moderate` reported **0 vulnerabilities** after the update.
- Browser: `frontend/e2e/connected-care.mjs` passed using real Chromium against an explicitly provisioned disposable synthetic database. It exercised doctor login and provisioning, one-time credentials and forced change, care-plan creation/update, sputum with image, symptom check-in, breakfast/lunch/dinner, hydration, activity, doctor review, patient notifications/read navigation, and negative role/record checks. Landing and patient layouts were checked at desktop and 390px mobile width. It does not exercise every page/breakpoint or all security/clinical risks.
- The sandbox did not have Python 3.12, which the repository's exact pinned NumPy requires. Backend tests ran on Python 3.11 with compatible independently resolved packages (FastAPI 0.162.0, NumPy 2.4.6, pandas 3.1.1, LightGBM 4.7.0, scikit-learn 1.9.1); the exact pinned Python 3.12 environment remains to be verified. Node 22.22.3 was used. One upstream Starlette TestClient deprecation warning was observed.
