# Testing and QA

Run in a disposable synthetic environment: `python -m pytest backend/tests -q`, `npm --prefix frontend ci`, `npm --prefix frontend test`, `npm --prefix frontend run build`, and `npm --prefix frontend audit --audit-level=low`. CI uses Python 3.13 and Node 20. Browser harnesses in `frontend/e2e` require explicit disposable credentials; several write synthetic test records and must never target production. See [release readiness](FINAL_RELEASE_READINESS.md) and [application audit](COMPLETE_APPLICATION_AUDIT.md) for dated evidence and gaps.

Automated axe and responsive checks do not establish accessibility compliance. Full manual keyboard, screen-reader, populated/error-state, zoom and real-device review remain required. Hosted CI and live E2E cannot be inferred from local test success.

Phase 1 local results on 2026-11-06: Python 3.13 pinned backend 122 passed; Node 22 frontend 65 passed and build succeeded; npm audit 0; five disposable care journeys; partial/empty doctor journey and 96 plus three automated axe/overflow scans passed. See the current audit for scope and caveats.

Phase 2: `npm run test:e2e:patient-management` exercises only an explicitly configured disposable synthetic database, creates a fictional profile, provisions one disposable account and records a follow-up completion. Never run it against production or valuable data. `npm run test:e2e:partial` covers partial/empty doctors. See the application audit for current results, prior failures and remaining verification.

Phase 3: `npm run test:e2e:login-throttle` intentionally locks the explicitly configured disposable synthetic account for the login window; never run against production or valuable accounts. Local backend 130 passed; frontend 71 passed and build/audit passed.

Phase 4: `npm run test:e2e:care-queue` requires an explicitly configured, pre-populated disposable synthetic queue of at least 51 items. It checks pagination, open states, filtering, selection and three automated axe/overflow scans; see the audit for execution results and limitations.

Phase 5: `npm run test:e2e:focused-queue` **mutates** a pre-populated local disposable synthetic fixture; it requires `E2E_DISPOSABLE=1`, a loopback `E2E_BASE`, credentials and Chromium. Record #1 for all five types must exist on the assigned patient and lie beyond the recent history caps; upload #1 must have a downloadable test PDF and follow-up #1 must be due and linked to check-in/upload #1. Never run it against valuable data. The script reviews and completes those records, checks exact IDs/context, keyboard focus and runs three axe/overflow scans. See the audit for execution results and remaining manual checks.

Phase 6: `npm run test:e2e:patient-history` requires a local disposable fixture with a doctor assigned to PG-0001, another doctor assigned elsewhere, a linked patient, 101 check-ins/uploads/reviews/plan versions and 501 diary/daily records (including shared and private reviews); provide `E2E_DISPOSABLE=1`, `E2E_BASE`, `E2E_DOCTOR`, `E2E_OTHER_DOCTOR`, `E2E_PATIENT`, `E2E_PASSWORD`, and `E2E_CHROMIUM_PATH`. It reads histories, downloads a synthetic PDF and signs in but does not write care records. It checks six histories, patient/doctor isolation, shared-review filtering and three automated axe/overflow scans. Never use valuable or production data.

Phase 7: `backend/tests/test_care_write_races.py` commits a session revocation on a separate SQLite connection immediately before the protected transaction for every listed care mutation, and checks that no records, review states, audit events, notices or staged files remain. It also exercises assignment removal, patient relink/unlink, status and expiry changes, synthetic-marker changes, upload attachment removal after staging, idempotency after relinking, and the reverse ordering where a revocation waits behind an acquired write lock. These are deterministic local integration tests, not exhaustive concurrency or distributed-storage tests. On 2026-11-07 the pinned local backend suite passed 142 tests, frontend passed 83 tests, the build and npm audit passed, and one fresh disposable Chromium patient–doctor care journey passed. Selected research snapshots matched `origin/main` and frozen assets were unchanged. This does not establish hosted CI, live deployment, production persistence, manual accessibility or independent security review.

Phase 8: `backend/tests/test_research_authorization_races.py` tests session revocation and assignment removal between initial auth and the authorized snapshot across the eight original per-twin methods plus portal explanation/scenario, and between scenario calculation and commit. It checks snapshot ordering when assignment and state change after a read snapshot starts, unchanged twin states, and successful scenarios/interventions. The full local pinned backend suite passed 152 tests; the frontend suite passed 83 tests, build and npm audit passed. The initial whole-suite runs were terminated near the end while repeatedly initializing large research engines; the test fixture was changed to reuse one module-scoped disposable engine, and the complete suite then passed. Selected research snapshots matched `origin/main`; frozen assets were unchanged.

`npm run test:e2e:research-transactions` **writes scenarios and an intervention** and requires `E2E_DISPOSABLE=1`, a loopback `E2E_BASE`, `E2E_DOCTOR`, `E2E_OTHER_DOCTOR`, `E2E_DOCTOR_PASSWORD` and `E2E_CHROMIUM_PATH`. Both doctors must share the disposable test password; the first must be assigned PG-0001 and the second must not. It checks explanation and scenario UI, both scenario APIs, original twin preservation, intervention, logout and cross-doctor denial. Run only on a fresh disposable database, never production. The local journey and separate partial/empty cohort journey, including three axe/overflow scans, passed. These checks are not hosted or manual accessibility verification.

Phase 9: `backend/tests/test_portal_read_races.py` tests session revocation after initial authentication and before the read snapshot across portal identity, patient list/detail, exact records, history, care plan, sputum/daily/summary, environment, upload metadata, notifications, queue, summary and validation. It checks doctor unassignment, patient unlink and filtered collection results, temporary-password expiry, consistent detail/twin snapshots, environment reauthorization after the provider returns, and download completion after an earlier authorized snapshot. The full pinned local backend suite passed **161 tests**; frontend passed **83**, build and npm audit passed. A disposable browser journey traversed six complete histories beyond earlier caps, downloaded an old synthetic PDF, checked sharing/isolation and passed three axe/overflow scans; a separate fresh disposable patient–doctor care journey passed. Selected research snapshots matched `origin/main`; frozen files remained unchanged. This is not manual accessibility, production or exhaustive concurrency verification.

Phase 10: `backend/tests/test_enhanced_write_races.py` exercises post-auth revocation for registration, observation, review, notification and alert writes; reassignment and synthetic-marker changes; registration retry isolation; SQLite write-lock ordering; successful writes; and rollback when notification/history/audit insertion fails. The complete pinned local backend suite passed **170 tests** after stopping disposable servers (an earlier run with them running was terminated near the end); frontend passed **83 tests**, build and npm audit passed. Selected research snapshots matched `origin/main`, and frozen assets were unchanged. These tests do not prove universal race safety or production readiness.

`npm run test:e2e:enhanced-write-authorization` writes fictional records and needs `E2E_DISPOSABLE=1`, a loopback `E2E_BASE`, `E2E_DOCTOR`, `E2E_OTHER_DOCTOR`, `E2E_PASSWORD` and `E2E_CHROMIUM_PATH`. Both doctors must share the disposable password; the first must be assigned PG-0001 with a new seeded alert, and the other must not be assigned that record. Run only against a fresh disposable database, never production. The local browser journey passed registry UI registration/observation/review and persistence, API notification/alert updates and cross-doctor denial. This does not establish hosted behavior or manual accessibility.

These tests do not establish hosted behavior or cover all enhanced routes.
