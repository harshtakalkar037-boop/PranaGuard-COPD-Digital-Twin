The script advances replay and records one scenario, and refuses existing DB or output paths. Never supply a production path.

The harness writes synthetic care entries: **never point it at production**. A first new run timed out due to an overly exact form-label locator, then the test locator was corrected and all five passed on a fresh DB. `frontend/e2e/accessibility.mjs` and `frontend/e2e/scoped-research.mjs` require explicit disposable credentials and Chromium; the scoped check creates login sessions and may update the assigned synthetic notification; do not run it against production. Random credentials were held in memory and test DBs/uploads removed.

Independently review concurrent registration, assignment and session revocation. Maintain fail-closed restrictions meanwhile.
2. Complete manual keyboard, screen-reader, focus, dialogs, zoom, populated/error-state and responsive review; automated checks alone are insufficient.
3. Verify provider connectivity, configured production routing and live persistence with an authorized operator, including private uploads, credentials, backups and an isolated restore. Do not treat local SQLite as production proof.

5. Run hosted CI and independently review scientific regression. Obtain clinical governance review; research outputs are not diagnoses, treatment recommendations or proof of clinical validity.

## Deployment and rollback planning (not performed)

These are planning requirements, not approval or commands to deploy:

- First resolve the blockers above and obtain explicit deployment authorization. Identify the real frontend and API targets, exact release revision, environment variables, provider configuration and persistent DB/upload volumes without exposing secrets. Reconcile the two repository hostnames.
- Take and verify a recoverable, consistent backup of the database and private uploads; rehearse restore in an isolated environment. Record current deployment revisions and monitoring baselines. Ensure all records are authorized and synthetic for this prototype.
- Rehearse migrations and all tests on a copy. Migration 006 is additive and does not rewrite existing hashes, but old `must_change_password` users intentionally fail closed. Plan administrator-led resets and secure delivery without logging credentials or automatically resetting accounts. Confirm the new code and schema are compatible before enabling traffic.
- Deploy only through the authorized operator's reviewed release procedure, preferably to a staging environment first; run explicit end-to-end authorization, patient ownership, research, provider, backup and session checks. Stop the release if any check fails.
- For rollback, use a tested, approved compatible code/schema plan and verify data integrity and access controls. Older code may not enforce the new single-use/expiry policy, so rolling back application code alone can weaken credential security; revoke affected sessions and reissue credentials under an independently reviewed safe procedure. Do not blindly restore an old database over new data or run destructive reset scripts. Confirm routing, logs, persistence, access and recovery after any rollback.
