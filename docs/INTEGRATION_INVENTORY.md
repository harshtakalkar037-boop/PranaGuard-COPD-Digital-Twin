## Baseline and scientific assets

Read-only inspection found 120 profiles (`PG-0001`–`PG-0120`) in `data/patients.json` and 172,800 hourly rows for 120 distinct IDs in `data/synthetic_longitudinal.csv.gz`; the generation manifest records 1,440 hours per patient. `artifacts/models.joblib`, evaluation and split manifests are existing frozen outputs. `TwinEngine` verifies the longitudinal file against the model bundle before inference. No regeneration, training, reset, or model changes are permitted for this redesign. `features.py` defines fixed risk thresholds (0.15/0.35) and existing 24/48/72-hour predictions. Historical ambient environmental features are already in the fitted pipeline; separate current city context is not fed into that frozen pipeline. Preserve this distinction.

## Critical baseline issues to address before presentation

1. `main.py` currently leaves research endpoints open and the doctor research route does not check portal sessions. The old `/api/*` endpoints and enhanced registry can expose records independently of `/api/portal/*` assignment checks. Legacy writes are also open when `PRANAGUARD_ADMIN_TOKEN` is absent. Authentication must be enforced server-side without exposing portal data; the legacy mode must remain explicitly isolated.
2. Research and care are separate shells; switching loses selected context and `/doctor/dashboard` currently lacks a logout/session gate. Five patient accounts do not imply assignment of all 120 records. A trusted admin should assign existing verified synthetic records to the demo doctor, with no automatic reassignment of real accounts.
3. Startup bootstrap upserts password hashes, silently resetting account passwords on every boot when configured. It must become insert-only and reject incompatible existing links/roles transactionally, rather than overwriting credentials.
4. Existing `docs/PORTALS.md` describes stronger legacy isolation than this baseline actually implements; implementation and documentation must be reconciled.
5. Browser-facing `VITE_API_BASE_URL` may override same-origin proxy and has an escaping issue in its trailing-slash expression; the production deployment must be checked separately, not inferred from a healthy response.

## Phased verification plan

Use only disposable test SQLite databases and synthetic uploads. Run migration/idempotency and portal authorization tests; existing legacy tests explicitly enable isolated mode. Add tests for research doctor/patient/anonymous access, cross-patient links, bootstrap idempotency and password preservation. Run original backend/frontend suites, build and full real-browser research/care journeys across viewports when browser dependencies are available. Perform live deployment testing only with explicit authorization, real access and controlled demo accounts; it is not completed by local tests. No production account or database changes were made during this audit.

## Phase 2 work in progress

Research API access has been changed from public access to a doctor bearer session requiring assignment to **every existing synthetic patient record**. This conservative whole-workspace gate is necessary because original cohort, alert, enhanced registry and device endpoints return unscoped lists. It does not grant cohort access to partially assigned doctors; a trusted operator can assign the existing frozen cohort with `portal_admin assign-cohort`. If other registered synthetic records exist, they must also be explicitly assigned before this workspace can open. A non-synthetic database record blocks the entire workspace. This is intentionally fail-closed, not fine-grained scoping. A later integration change atomically assigns a portal-mode fictional registration to its registering doctor so that doctor retains access; other doctors still require explicit assignment to the new record. Unauthenticated legacy research stays available only in explicitly isolated legacy mode. The secure workspace currently uses polling rather than the unauthenticated WebSocket.

Optional bootstrap now leaves existing password hashes unchanged; `assign_cohort: true` explicitly assigns original synthetic profiles only. It still creates missing configured accounts/links on startup and is not a production identity-management system. Account provisioning must be done only in an approved synthetic environment; no live accounts have been provisioned here. The research shell now checks a doctor session and carries selected patient IDs into care links. This does not yet unify the shells or complete the requested redesign. Verification results are tracked separately; do not treat the baseline or this phase as production-ready.
