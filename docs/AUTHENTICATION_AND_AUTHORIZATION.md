# Authentication and authorization

See the [route matrix](ROUTE_PERMISSION_MATRIX.md) for endpoint requirements and [portal guide](PORTALS.md) for provisioning. Portal sessions are opaque bearer tokens, stored hashed in SQLite; passwords use salted scrypt. Temporary demo credentials are random, expire, and require a password change. Patient accounts are linked to one record; doctors are explicitly assigned. Portal record access and patient-linked notifications require a current link or assignment and an explicit JSON boolean synthetic marker. Doctor historical cohort queries use a read snapshot for assignment, state, trends and counts; both validation endpoints require full original cohort assignment. Secure-mode WebSockets are disabled. Remaining global operations require a conservative one-doctor full-workspace gate and administration must be quiesced.

The login endpoint locks a case-insensitive username for the remainder of a 15-minute window after five failed attempts, including nonexistent usernames. Successful authentication or a trusted administrator password reset clears that username window. SQLite stores only a SHA-256 username key and counts, not passwords. This deliberately permits targeted account lockout and does not protect public registration, password spraying across many usernames, or distributed infrastructure; edge/IP abuse controls, monitoring and recovery procedures are still required. SessionStorage is JavaScript-accessible. Hardened session architecture, MFA, upload malware scanning, consent, production observability and independent security review remain open. Never use real patient information or enable unsafe legacy mode on a network.

## Care-write authorization ordering

Check-ins, uploads, clinical and diary reviews, sputum changes, care-plan versions, daily-care entries/reviews, demo provisioning, follow-up completion and portal notification read updates revalidate the hashed bearer session, expiry, role and password-change state after acquiring a SQLite `BEGIN IMMEDIATE` write lock. The assignment/link and synthetic checks and associated database writes, notifications and audit entries then share that transaction. Patient writes also compare the link seen at initial authentication with the link under the lock; a changed link returns 409 rather than sending an in-flight submission to a different patient. A reused daily-care submission key cannot return an entry from a previous patient link. The raw bearer token and internal session hash are not added to API response objects.

This defines an ordering, not retroactive cancellation: a revocation, reassignment or unlink committed before the write lock is acquired is observed; one that waits behind an already authorized write takes effect after it commits. Session expiry is checked at the locked authorization point, not continuously until commit. A link that changes away and back before the second check is not detectable without versioned links; nor does this mechanism identify a browser form rendered before an earlier completed relink. Administrative writers must use the same SQLite database and its locking for this guarantee. Lock contention may delay writes and eventually time out.

Uploads are read and staged before the write lock to avoid locking during file transfer. After staging, session, link, synthetic status and any diary attachment are checked again in the write transaction; failed transactions attempt to remove the staged file. A process or machine crash can still leave an orphan file and requires operational cleanup. This is not a filesystem/database atomic commit or a security certification. Other legacy/global operations and nontransactional filesystem delivery do not share this write-lock guarantee; some in-flight revocation and authorization windows remain, especially across separate database/engine/filesystem operations. Administrative changes should be quiesced for global operations.

## Patient-specific research ordering

In secure mode, the original historical patient, history, versions, explanation, scenario-list and intervention-list endpoints revalidate the bearer session and doctor assignment against the same SQLite read snapshot as the returned record. The portal explanation uses the same policy. An already established read snapshot can still finish after a concurrent revocation; this is an ordering guarantee, not retroactive cancellation. Derived history and explanations use that snapshot's persisted states; immutable in-memory cohort inputs and the frozen models are not protected by SQLite locks.

Both the original and portal scenario endpoints authorize and load their source state in one read snapshot, calculate outside the database write lock, then revalidate the session and assignment under `BEGIN IMMEDIATE` before inserting or returning a result. A revocation or unassignment committed during calculation rejects the request without a scenario row. The original research intervention write checks session, assignment, synthetic marker and source state under the same write lock as insertion. A revocation blocked behind a write takes effect after that write. In-process replay and scenario work also use the engine lock; out-of-band changes to twin state during model computation are not globally serialized, and assignment changes away and back are not version-detected. Unsafe legacy mode deliberately has no portal authorization and must remain isolated.

These changes do not cover every enhanced registry, alert or unscoped global endpoint; see the later enhanced-write section for selected exceptions. Such routes can still have in-flight session/authorization windows, and administrative changes should be quiesced when using global operations. They are not proof of production security.

## Portal read ordering

`/me`, patient lists and detail, queue and summary, exact queue records, paginated and older care histories, care plans, daily summaries, notification lists, portal validation and download metadata now revalidate the session in the same SQLite read snapshot as their database data. Patient-specific reads also verify the link or assignment and explicit synthetic marker in that snapshot; patient link changes since initial authentication return 409. Detail retrieval uses the same snapshot for care data and persisted twin/history state. `/me` remains available during a valid forced-password-change session and rechecks its temporary credential expiry.

The patient environment route checks session, assignment and patient city before the provider call and again after it, returning 409 if a persisted fictional patient's city changes. The provider call is outside the SQLite transaction and may have already made a request or updated its cache before a later authorization failure; it cannot be undone. Historical cohort city comes from the frozen engine profile as before. Context is city-level, not personal exposure.

A read snapshot established before a revocation or unlink may finish after it; authorization is not retroactive. Download authorization and metadata share a snapshot, but file bytes are delivered from the filesystem afterward and an in-progress download is not cancelled upon revocation. SQLite and file storage are not a single transaction; external modification, deletion or replacement of stored files is not prevented by a read snapshot. Link changes away and back cannot be detected without versioning, and the new checks do not close all enhanced registry, alert or global-operation race windows (see the enhanced-write section below). No production security guarantee is implied.

## Enhanced and legacy alert writes

In secure mode, fictional registry registration revalidates the session and account under `BEGIN IMMEDIATE`; patient creation, doctor assignment, audit and idempotent retry authorization share that transaction. An existing request ID is returned only when its record remains assigned to the doctor and has the explicit synthetic marker. Registry observations and reviews revalidate session, assignment and synthetic marker under the same write lock as their inserts; observation-triggered notifications and review audit records commit or roll back with the primary write. Review state version is read on that connection while holding the engine lock. Enhanced notification updates revalidate session and perform their existing doctor/assignment/synthetic scoping, update, history and returned detail in one write transaction. Legacy alert updates likewise revalidate session and apply their existing assignment/synthetic scope under the write lock. Unsafe isolated legacy mode intentionally does not perform portal session checks.

The locked check orders writes against other SQLite writers, not against elapsed time or already-completed work: a revocation or assignment change committed first is observed, whereas a change waiting behind the write takes effect afterward. Session expiry after the check and assignment changes away and back are not detected. Alert synchronization and broadcasts after a committed write are separate effects. Independent notification/alert reads, devices, simulator, environment and other global operations do not all share this transaction guarantee; some still have in-flight authorization windows and global operations require quiesced administration. These local changes are not a security certification.

## Enhanced registry read ordering

In secure mode the registry collection revalidates the doctor session in the same SQLite read snapshot as assigned synthetic profiles, latest model states, device counts and manual-baseline status. The patient detail revalidates the session and assignment in the snapshot used for profile, registration, baseline, persisted twin state/history, devices/readings, monitoring, observations, interventions, archived reviews and scoped notifications. Before this snapshot, legacy-alert synchronization may write: it rechecks the session and patient access under its own `BEGIN IMMEDIATE` transaction. The detail then obtains city-level environment context outside SQLite and revalidates session, assignment, synthetic marker and persisted city again in a new read snapshot; a changed city returns 409. Explicit isolated legacy mode still has no portal authorization.

An already-established collection snapshot may finish after revocation or unassignment. Detail data can become stale after its snapshot even if the later session/assignment/city check succeeds; that later check does not make provider access, sync and the data snapshot atomic. Synchronization can commit and a provider call or cache update can occur before a subsequent authorization failure. Session expiry after the final check and assignment changes away and back are not detected. Independent enhanced notification/alert reads, device/simulator and global operations still have in-flight authorization windows and global operations require quiesced administration. These changes are not production security certification.
