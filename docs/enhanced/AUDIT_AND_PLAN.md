## Phase 1: findings
1. **Architecture:** React/Vite/TypeScript → REST/WebSocket → FastAPI → shared causal features/LightGBM bundle and SQLite state engine. Browser API helper supports `VITE_API_BASE_URL`; local Vite uses a proxy. Deployment CORS exists in the supplied fork.
2. **Navigation:** overview, patient twins, explainability, scenario studio, model validation, care activity, system/data status. Original views will all remain.
3. **Design/components:** `styles.css` supplies the visual identity: sidebar `#103b34`, page `#f6f8f7`, ink `#203e36`, primary button `#1b6b55`, white bordered panels, 6–9px corner radii, restrained shadows. System-font stack starts with Inter but no external font load. Lucide and Recharts are already installed. Breakpoints:1600/1250/1000/720px and reduced motion. Reusable `Panel`, `Pill`, `Notice`, `MetricCard`, `Loading`, `Empty`, `CohortTable`, `RiskChart`, `TextLink`, `api`, `post`, `useRemote`. Original stylesheet, Tailwind config and shared visual components will be byte-preserved; new CSS is scoped.
4. **Database:** existing `patients(profile JSON)`, immutable `states`, `alerts`, `interventions`, `scenarios`, `meta`. Foreign keys and WAL are enabled; there is no versioned migration mechanism. The prior synthetic workspace DB was inspected read-only:120 patients,3000 states, cursor1039/version25. A backup is copied to the isolated working copy without reset. New tables/indexes will be additive with migration checksums.
5. **API:** cohort/patient/history/version/explanation/scenario, alerts and review actions, validation/status, replay start/pause/step/reset, WebSocket invalidation and optional demo admin header.
6. **Alert implementation:** one unresolved experimental72h model alert per patient, with persisted acknowledgement/resolution. Interventions are separate append-only notes within a replay run. No general notifications, category filters, unread state, lifecycle history or email channel exist.
7. **Environment:** eight historical JSON caches and an explicit fetch script. No current-context service exists. Actual current Open-Meteo requests succeeded during audit. IMD's documented current-weather endpoint returned401 (`API key missing`); CPCB/Data.gov.in could not be verified due connection/catalog failure. Those providers will not be represented as connected.
8. **Tests:** existing pytest tests cover shared features, leakage guards, inference, exact TreeSHAP, scenario isolation, replay, SQLite and alert/action lifecycle. RTL/Vitest covers original controls; a Chromium script exercises the actual app. Their historical reports will not be overwritten or treated as newly executed evidence.
9. **Risks identified:** seeding currently uses `INSERT OR REPLACE`; reset deletes all action rows; new patients must not be inserted into the frozen raw longitudinal CSV; there is no safe72h onboarding route; optional live source fields must not flow into trained models; sidebar needs bounded scrolling for new items; local proxy fallback port differs from the documented backend port.

## Phase 2: implementation plan and dependencies
1. **Protection first:** hash all model/evaluation/split/history artifacts, original CSS/shared components and historical caches. Preserve source DB row digests. Never retrain/regenerate historical data.
2. **Patient management:** additive registration/metadata tables; server IDs and request idempotency; fictional identity confirmation; validated fields; all-patient listing/search/status/city filters and complete profile. Registration depends on migration and common validation. Manual baseline values are reference information only and do not count as72h observed data.
3. **Device simulation:** association and generic capability catalog, simulation lifecycle, deterministic synthetic samples at configured wall-clock intervals. Background generator submits through the same Pydantic ingestion REST endpoint used by clients. Persist event IDs, timestamps, units and source. Idempotent events cannot duplicate readings or monitoring versions. No physical hardware/commercial compatibility claim.
4. **Environment:** independent backend provider/cache service; current modelled air/weather for4 allowlisted cities; partial/stale/offline states and historical fallback. Timestamps and AQI scale remain explicit. No live fields enter `TwinEngine` prediction features. IMD/CPCB are documented as not integrated, pending access/licensing verification.
5. **Notifications:** category/status/unread/history tables, legacy alert bridge and review transitions; rules explicitly labelled demonstration-only. Device, symptom, environment and service events are separate from frozen-model alerts. SMTP test/outbox channel uses environment-only configuration and sends no patient data; no automatic ML email.
6. **Provenance/UI:** five new nav entries (Patients, Device integration, Environment, Notifications, Data sources) use existing components and palette. Existing model/twin views remain historical; new monitoring profile links to them only for the original cohort. Device overlays never silently replace model inputs.
7. **Tests/docs:** backend/RTL/build/browser checks; migration row preservation, no-model-change checks, provider mocks/failures, baseline/ingestion/dedupe, notifications and local SMTP capture. Publish only actual executed results. Extend README/API/provenance/env docs, add device/notifications guides and a final ZIP.

## Onboarding/model eligibility decision
A new demo registration is not automatically a new validated model input. Devices collect distinct hourly observations over real elapsed time;72 frequent samples are not72 hours. Even after warm-up, device-only data lack the full compatible clinical, symptom/adherence/sleep and historically aligned environmental feature frame. Predictions remain unavailable rather than inventing features, bypassing warm-up or mixing live context into historical models. The original120-patient experimental analysis remains available and unchanged. This is an explicit scientific boundary, not a claim of newly validated inference.
