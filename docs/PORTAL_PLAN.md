# Portal audit and implementation plan

The existing application is a React/Vite dashboard using Inter, #103b34 sidebar, #28594b active navigation, #1b6b55 buttons, #f6f8f7 background and #203e36 text. The backend is one FastAPI app; Store owns SQLite and checksum-verified, additive SQL migrations. The synthetic cohort and frozen model artifacts are loaded by TwinEngine; enhanced services add registry, device, notification and environment tables. No database is checked in. Existing legacy APIs and websocket are unauthenticated for reads, and writes are optionally protected by a shared demo token; the legacy cohort and registry endpoints cannot enforce assignments. Exposing those routes alongside personal records would bypass portal permissions.

Plan: add a checksum-verified migration for accounts, assignments, sessions and workflows; use the same Store and engine; expose a scoped portal router; provide an explicit local administrator CLI to create doctors and link existing records. Block all legacy REST and WebSocket routes by default, retaining them only in explicitly enabled, isolated synthetic demo mode. Build the landing and portal experiences using the established colors and components. Validate ownership on every endpoint, store private uploads outside static directories, and test cross-account access and workflows. Do not change models, generated datasets or historical data. The original dashboard's full technical features remain available only in the explicitly unsafe demo mode, not in the protected portal, until all of its APIs can be individually scoped.
